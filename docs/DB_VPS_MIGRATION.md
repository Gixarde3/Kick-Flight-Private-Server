# Player database migration to the VPS

Migration completed on 2026-10-07. The production API now uses PostgreSQL 17.11 on the same VPS.

## Starting point

The API used PostgreSQL 17.11 from an external provider through `PlayerStore__DatabaseUrl`.
`PlayerStore__ConnectionString` was empty. The source database was about 8.66 MiB, had only the built-in
`plpgsql` extension, and contained about 2,525 rows across four tables. The VPS inventory at assessment was
2 vCPUs, 7.7 GiB RAM, and about 22 GiB free disk.

The API store uses Npgsql and PostgreSQL-specific SQL. SQLite remains the separate store for balance-panel
users and sessions; it is not part of this migration.

## Restore rehearsal

A consistent external `pg_dump` snapshot was restored to PostgreSQL 17.11-alpine before cutover. The snapshot
was 164,966 bytes. Comparison passed for four tables and all 2,525 rows: table counts and per-row JSON MD5
hashes matched. The schema had seven constraints, six indexes, no identity columns, and one sequence;
`player_id_seq` matched at `last_value=1,002,214` and `is_called=true`. Column definitions, player IDs,
sessions, and the `plpgsql` extension matched.

## Production cutover and verification

Only the API writer was stopped under the deployment lock. The final external dump was 165,348 bytes.
It contained four tables and 2,535 rows: players 194, player_ranks 115, schema_meta 1, sessions 2,225.
Before enabling local writes, the restored database matched the external canonical JSON fingerprint exactly
(9,014 bytes including newline): row hashes/counts, column defaults and identity definitions, seven
constraints, six indexes, extension, and the sequence value/is_called. The source had no identity columns;
IDs are allocated through player_id_seq. No orphan sessions/ranks were found in rehearsal.
The new local API started at 19:00:13 UTC. The exact initial shutdown timestamp was not retained; do not
interpret the earlier downtime estimate as a measured duration.

A synthetic device authenticated through the public API; `/tutorial/end` persisted a name; `/startup/index`
returned tutorial status 207 and `/home/index` returned that name. After restarting both PostgreSQL and API,
the pre-restart session token still worked, the name persisted, and reauthentication returned the same player
ID. Synthetic player records were removed afterward; sequence advancement was deliberately retained.

The API has ConnectionString host `postgres`, with DatabaseUrl absent. PostgreSQL is 17.11, its app role
has LOGIN but no SUPERUSER/CREATEDB/CREATEROLE/REPLICATION, and storage is `deploy_postgres-data`.
An active API TCP database connection pointed only to the local PostgreSQL container; no external
PostgreSQL TCP connection was present. Port 5432 is unpublished. The external cutover fingerprint was
checked again after the migration and remained identical: the source has not been deleted or disabled.

`/health/ready`, the public landing page, balance login page and CDN responded successfully. The CDN
resource hash matched its catalog. All five masters overrides retained their original SHA-256 hashes.
SQLite was not migrated, restored or changed by the migration scripts. Its physical hash did change during
preparation: the panel journal recorded a successful login at 18:51:22 UTC, matching a new session timestamp
in SQLite. Two users and two sessions were present afterward. A successful login was observed in the live
service journal; no owner credentials were available to repeat that login independently. A synthetic invalid
login returned 401.

Photon kept the same container, start time, luxon_server process and TCP/UDP port bindings throughout.
Its health status remained healthy. A full client Photon handshake/match was not exercised; the HTTP Photon
health check alone is not proof of that flow.

The timer is enabled and an actual systemd backup run completed with Result=success. A dump generated by
the daily backup script was restored into a disposable database and matched its source fingerprint exactly;
the disposable database was then removed. Backup files are mode 0600 under a mode 0700 directory.

Rollback restoration was rehearsed on a disposable PostgreSQL database with a post-cutover marker and
sequence, and both survived the restore. An injected mid-restore failure rolled back atomically, preserving
pre-existing destination data. The final script's actual configuration parsing and cancellation path also
passed on this VPS. A real external fingerprint query with an intentionally different private baseline
also proved the drift guard aborts before stopping the API or restoring data. Production rollback was intentionally not run because it would overwrite the retained
external source.

## Deployment protection

Root `.env` contains `KF_DB_MODE=local` and no DATABASE_URL. Old CI code that forces the external profile
fails Compose validation before restarting services; the workflow does not inject DATABASE_URL and rsync
preserves `.env`. Until the PR is merged, old CI deployments will fail safely. Updated CI defaults to local
and honors external mode only when the guarded rollback explicitly persists `KF_DB_MODE=external`.


## Runtime topology

The API uses `deploy/docker-compose.vps.yml`; PostgreSQL 17.11-alpine uses the persistent Docker volume
`postgres-data` on the private Compose `backend` network. Port 5432 is not published. The application login
is `kickflight` and is configured as a database owner without superuser or role/database-creation privileges.
The root `.env` holds `KF_DB_PASSWORD` and a separate `KF_PG_SUPERUSER_PASSWORD`; both remain outside Git.

Daily dumps are stored under `/opt/kickflight/.local/db-migration-20261007/backups/`, with 14-day retention,
private directory/file modes `0700`/`0600`, and a systemd timer at 02:15 UTC. A same-VPS backup does not
protect against loss of the VPS; maintain an encrypted off-host copy for disaster recovery.

For rollback after local writes, run the guarded and versioned
`/opt/kickflight/scripts/rollback-kickflight-db-to-external.sh`. It checks the external database against the
private `external-target.json` destination and `external-baseline.json` cutover fingerprint (including schema, table rows, constraints, indexes,
extensions, and sequences), stops the API writer, saves a fresh local dump and a pre-restore external dump,
restores local state in one transaction, and only then starts the API with the saved pre-cutover configuration.
It aborts without overwriting the target if the external DB drifted after the cut. Switching the Compose
profile alone would discard writes made after cutover.

## Restore a local backup

Inspect the dump with `pg_restore --list` first and rehearse into a separate database if its provenance is
uncertain. Then, in an authorized maintenance window (never alongside CI), use the following on the VPS.
The restore replaces player data with the chosen backup and therefore loses player writes made after it.
The rollback-to-external script instead dumps the current local state to preserve post-cutover writes.

```sh
cd /opt/kickflight
exec 9>.ci/deploy.lock
flock -x 9
docker compose --env-file .env -p deploy -f deploy/docker-compose.vps.yml stop api
scripts/backup-kickflight-db.sh </dev/null
# Replace the path with the verified dump; do not use pre-cutover.env as the active local env.
docker exec -i deploy-postgres-1 pg_restore -U kickflight -d kickflight \
  --clean --if-exists --single-transaction --no-owner --no-acl < /absolute/path/to/verified.dump
docker compose --env-file .env -p deploy -f deploy/docker-compose.vps.yml up -d --no-deps api
docker compose --env-file .env -p deploy -f deploy/docker-compose.vps.yml restart cdn grpc
# Wait for readiness, then verify a real persisted player/session through the API.
curl --fail http://127.0.0.1:18080/health/ready
```

On a failed restore, the transaction leaves the previous database intact; restart the local API and proxies
and verify it before reopening writes. The rollback script serializes with CI using `.ci/deploy.lock`,
checks the saved external destination and two external fingerprints, and refuses to overwrite external drift.
Keep pre-cutover.env, external-target.json and external-baseline.json private alongside the dumps.
