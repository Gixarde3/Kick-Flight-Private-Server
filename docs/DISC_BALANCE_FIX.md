# Disc balance corrections

## Source and interpretation

`docs/disc_damage_expectations.json` transcribes the 87 finite damage expectations in the user's `discs_info.md` and records the original name, measured actual/expected values, and notes. Those expectations are the authority for these corrections; `docs/disc_cards.json` / Appliv is a fallback for cards not measured in the attachment. The attachment compares damage from a full Trial use against the kicker's attack value, while strings such as `0.05 ×20` describe a per-impact multiplier and an impact count. For a disc, the final multiplier is `Skill.coefficient × DiscSkillParameter._coefficient`. `DiscParameterUtil.CalcCoefficient` calculates `Mathf.FloorToInt(minCoefficient + (maxCoefficient - minCoefficient) * rate / 100)`, despite the Disc endpoints being floats. Therefore fractional Disc endpoints do not preserve fractional per-hit values. The corrected representation uses `Disc.minCoefficient = Disc.maxCoefficient = 1`, which yields exactly 1 at every growth level, and stores the expected per-hit multiplier in `Skill.coefficient`. The hit/tick count remains in the timeline and is not multiplied into either per-hit coefficient. Effects without an explicit damage coefficient (heals, buffs, movement, warp, and Snazzy Snail's slow) are intentionally not synthesized from damage data.

**Correction to the earlier 2026-10-07 audit:** the first endpoint-based change and its 87/87 floating-point audit were invalid. The audit compared configured float endpoints directly and did not model the client's integer floor. The v4 HP snapshots remain evidence that decoded damage was applied to HP (298 exact deltas plus 17 lethal clamps), but they do not establish that the expected 87 per-hit multipliers were correct. The corrected audit now models the runtime floor at every Disc growth rate.

The shipped `config/masters_*.json` tables are base data. On the VPS the API reads a matching file under `.local/masters-overrides/` first, so that runtime override wins over the shipped base. The production merge in `.local/pr-recon/merged-overrides/` starts from the Tanuki snapshot and changes only the 87 coefficient pairs, six specified condition triggers, and nothing else; it preserves the existing Princess Izana interval and both row-80 records. These private files are review artifacts and were not written to the VPS. The tracked base Disc/Skill masters carry only the same 87 coefficient corrections; the card pipeline's generated effect tables were not run into the production snapshot.

All 87 expected rows are mapped to a current Disc/Skill. Eight alternate names have explicit, evidence-backed aliases in the expectation file: Crocopeller/Propedile (プロペダイル), Vegedra/Hatakidora (ハタキドラ), Bratty Otty/Yanchara (ヤンチャラ), Volcortoise/Volcatus (ボルケータス), Wind Weasel/Kazetachinu (カゼタチヌ), Snotty Puff/Hanapoogon (ハナプーゴン), Rappit/Lapibit (ラピビット), and Armorlocaris/Armed Calis (アームドカリス). The stored evidence includes the Japanese name, N rarity, ATK subtype, neighboring list position, and matching expected multiplier. No unmatched expectation rows remain.

## Causes and changes

- The first attempted correction wrote fractional expectations to the Disc endpoints and set `Skill.coefficient=1.0`. Binary inspection showed that `DiscSkillParameter.GetCoefficient` at RVA `0x148EB00` calls `SkillMasterData.get_Coefficient`, loads `this._coefficient` at object offset `+0xD8`, and multiplies them (`fmul`). More importantly, `DiscParameterUtil.CalcCoefficient` at RVA `0x1638520` calculates the Disc value and tail-branches to `Mathf.FloorToInt` at `0x23E7D20`. The metadata types confirm `DiscMasterData.MinCoefficient/MaxCoefficient` are floats, `DiscGrowMasterData.Rate` is float, but `DiscParameterUtil.GrowParameter.Coefficient` is int. In `PlayerDeckParameter..ctor` (`0x1740B50`-`0x1740B7C`), that returned integer is converted with `scvtf` and passed as the float coefficient argument. The corrected pipeline instead writes Disc endpoints `1`/`1` and the expected fractional value into `Skill.coefficient`, so the runtime product stays exact at all growth levels. `PlayerDeckParameter.GetAttack` at RVA `0x1740E24` returns the stored `_totalAttack` or `_totalAttackPrimitive`; it does not apply the disc skill multiplier. The attachment's Attack 864 is from an earlier four-disc set, while the current test deck 4 is a different level-10 set, so comparisons must use the current battle's reported attack value.
- The generator could overwrite three intentional `ShotAttack` action types (10027, 10079, 10112) with `AutoMove` when applying card types. The apply pipeline now reapplies `DISC_ACTION_TYPE_OVERRIDES`, preserving their bullet timelines and, for 10112, its hit paralysis.
- Bomb/turret status conditions were configured for trigger type 5, which is consumed by `ConditionTrapAction`; the affected bomb/turret paths apply conditions carried with damage instead. The six affected skills (10041, 10049, 10082, 10097, 10105, 10128) now use `ReceiveDamage` trigger type 1 while retaining their bomb/turret type and damage behavior.
- Princess Izana's turret (10134) had a 2-second firing interval despite a 15-second lifetime and an expected five hits. The interval is now 3 seconds, corresponding to shots at 0, 3, 6, 9, and 12 seconds if the turret fires immediately. First-fire and expiration-boundary timing still need in-game verification. Raging Bulldog's 36-versus-37 observed hit discrepancy was not changed: its existing 0.4-second turret interval is consistent with about 37 opportunities in 15 seconds, and the notes alone do not establish a server defect.

Five user measurements intentionally differ from Appliv coefficients and therefore override them: Liberwolf (0.8 vs 1.0), Vampire Bat (3.0 vs 3.9), Magistork (3.4 vs 3.6), Glass Bomb (3.4 vs 3.2), and Poison Bullet (0.5 vs 0.7). The audit verifies all 87 explicit expected values against the generated masters; remaining 44 cards have no explicit damage coefficient and are categorized by effect type by the audit script.

## Repeatable pipeline and validation

Run from the repository root:

```sh
python scripts/apply_disc_cards.py
python scripts/audit_disc_coefficients.py
```

`apply_disc_cards.py` is the canonical pipeline: it applies card data, user expectation overrides, action overrides, and regenerates the associated skill effect tables. Running a separate generator remap afterward is not the canonical order; the card application path preserves `DISC_ACTION_TYPE_OVERRIDES`, which is covered by the audit. The corrected audit checks `Skill.coefficient × floor(Disc.minCoefficient + (Disc.maxCoefficient - Disc.minCoefficient) * rate / 100)` for every configured growth rate, rather than comparing the raw endpoints.

The corrected audit reports 87 explicit damage coefficients and checks the actual integer-floor calculation against all 50 configured Disc growth levels for each mapped skill; it also asserts fractional regression probes `0.05`, `0.63`, and `5.8`. Reapplying the canonical pipeline twice should be checked after any source data change, because it also regenerates associated effect tables. A served-master check must compare `Skill.coefficient × floor(Disc endpoints at the effective growth rate)`, not raw endpoints. `/health/ready` only confirms service/resource readiness and does not verify the battle coefficient formula.

These changes affect API masters only: no client code/APK source, Octo resource, CDN catalog, or resource revision was changed. The local API and Photon were running in the test worktree; the existing Octo cache was retained and no clean-boot test was performed. A first isolated diagnostic APK was mistakenly built with `KF_PHOTON=1`: that keeps `GameManager.InitializeReconnect` live, but its body was reused for diagnostic caves. The resulting record was malformed (`AttackType=1971011920`, outside the client's enum range -1..9), followed by a process abort in `ApplyHp → PlayerCharacter.SetHP → PlayerParameter.set_HP → GetMaxHP → KickerParameterMasterData.get_HpCorrection`. The reader rejects that record. This was an instrumentation/flag mismatch, not a balance result. A v3 APK built with the same default flags as the tested LAN production APK was byte-compared with that baseline; only the two hooks, two caves, and logger helper/data differed, and `InitializeReconnect` was `ret` in both. Its final capture `.local/run/logcat-damage-v3-final.txt` is a complete local match (`battle-791360261`) with the server's test-bot roster fixture active.

```sh
python scripts/audit_battle_damage.py .local/run/logcat-damage-v4-battle-end.txt --deck-ids 3010020,3010022,3010134,3010082 --hp-pairs
```

The reader keeps legacy v1 records separate from v2, where `damage_decoded_before_corrections` is the decoded `DamageInfo` value before later AI/ExtraHP corrections—not HP actually lost. Verified zero-based deck mapping applies to `AttackType` 2 (`Skill`) and 7 (`SummonTrapAttack`); type 7 uses the separate `SummonParameter` attack path, so these records do not validate the generic Skill coefficient formula. Type 5 (`Condition`) can retain the originating `AttackIndex`; it identifies the source slot but is not a direct-hit coefficient measurement. Type 1 (`WeaponBullet`) is never treated as a disc. Incomplete records and values outside the `AttackType` enum are discarded.

The final log has 331 framed/partial records: 314 complete records (24 Skill, 28 summon/trap bullet, 103 Condition, 134 weapon bullet, 22 direct weapon, 3 kicker-skill) and 17 truncated records discarded at log/restart boundaries. All seven bot rows in `battle-791360261` used deck 3 `[3010020, 3010022, 3010134, 3010082]`, level 10; the human used a different deck 4, so raw object IDs are retained and a deck must not be applied to every actor without first mapping the actor to the roster. Grouped by `AttackType=2` index, the log records slot 0 damage values 3570, 4865, and 5080 from actors 664624367, 835500727, and 313949712; slot 1 values 1766, 1973, 2102, 2879, and 3008 from actors 313949712, 664624367, 835500727, and 1468940215; and slot 3 values 591–1027 from six actors. If those slots belong to the bot fixture, they correspond to Raging Kong (expected 5.8), Volcatus (expected 3.8), and skill 10082 (expected 1.3), respectively. These are pre-correction decoded values, not actual HP loss or a normalized attack-stat comparison, so this sample does not establish an exact per-hit damage formula or refute a separate observed multi-hit total.

Type 5 slot 3 is attributable to Jack o' Lantern (3010082): `PoisonConditionAction.get_AttackIndex` reads the preserved `DamageInitializeInfo.AttackIndex`, and the human deck's slot 3 is Volcatus, not a poison disc. The v3 log had recurring poison ticks such as 627, 697, 836, and 1045; the served Poison row (id 73) has `effectValue=0.06`, `interval=1`, and `duration=10`. V4 adds snapshots at both sides of `SetHP`: 9810/9910 records victim, HP before subtraction, and damage after ExtraHP; 9811/9911 reads post-set HP through the verified `int32 PlayerParameter.get_HP()` getter. `--hp-pairs` pairs these by victim and order, reports `HPbefore - HPafter` as actual HP delta, and attaches the nearest preceding complete v2 record for that victim. It reports unmatched pre/post records separately and discards orphan posts rather than treating them as applied hits.

The final v4 capture `.local/run/logcat-damage-v4-battle-end.txt` has 315 complete v2 records and 315 matched HP pairs, with no unmatched pre/post or malformed v4 snapshots; 13 incomplete raw records were discarded. In every pair, `damage_decoded_before_corrections` equals `damage_after_extra_hp`. In 298/315 pairs, processed damage also equals actual HP delta. The other 17 are lethal clamps (`HPafter=0`, `HPbefore < damage`), such as 634 against 21 HP and 5900 against 1946 HP. This validates the v4 snapshots and separates per-hit input from HP lost on overkill. It does not validate the expected 87 coefficient values: the tested endpoint encoding was subsequently found to be floored to an integer and the capture lacks the controlled Trial-versus-expected normalization needed to infer those multipliers. The CSV artifact `.local/run/damage-v4-battle-end-hp-pairs.csv` includes each pair's raw and processed damage, HP before/after, actual delta, attack metadata, object IDs, and whether the deck attribution assumes the bot fixture.

Assuming the Type 2 records are from bot actors (the test had no manual player inputs; exact ObjectId-to-roster identity is not mapped), deck-3 slot 0 is Raging Kong (expected 5.8) and slot 1 is Volcatus (expected 3.8). Slot 0 recorded two hits: 5080 (actual delta 4368, lethal clamp) and 5510 (delta 5510). Slot 1 recorded six hits: 2231 twice, 2621 twice, 2879, and 3008; all deltas matched except the 2621 hit against 2557 HP. Slot 3 recorded 14 Type 2 hits and 100 Type 5 condition ticks from Jack o' Lantern's poison; damage matched actual HP delta except lethal clamps. The capture also contains 12 Type 7 index-2 summon/trap damage records, which map to Princess Izana in the bot fixture but use a separate `SummonParameter` attack path. Their coefficient semantics and complete shot count remain open. The seven bot rows all use deck 3; the human has deck 4. The CSV labels Type 2/7 disc attribution as a bot-fixture assumption. These controlled bot samples do not directly compare to the user's trial measurements: attacker stats, target state, repeated-hit totals, and the user's deck/cache context differ. Full Trial-vs-expected totals remain unverified.
